# 双授权操作上下文

## 修复原因

旧的 `galleryTransferContext()` 表示图片上传所用配置。在双授权场景中，图片上传可以选择 IOP，但橱窗、SKU 库存等仍需 TOP。将上传上下文附到这些请求上会固定错误协议，覆盖正常的按能力选路。

上下文绑定本身仍是必要的安全边界：修复的是获取上下文的用途，不是在请求失败后忽略上下文或改用另一份凭据重试。

## 客户端和后端约定

- `galleryTransferContext(operation?, payload?)` 对应现有 `POST /gallery-transfers/context/get`。旧的无参数请求保持图片上传语义。
- `operation` 必须是已登记的工作台操作。`payload` 为选路所需参数；指定它时必须同时指定操作。查询只返回不透明身份和配置标识，不执行操作、不授予权限。
- 通用调用使用 `callCapability`，并提供实际 `method` 和影响选路的参数，不能把所有通用调用视为同一能力。
- BFF、插件后台、可用性提示和实际请求使用相同的选路规则。调用仍执行原有身份、CSRF、可信发送方、契约和逐方法写入限制。

| 用途                         | 获取上下文的操作                                 | 双授权时的协议 |
| ---------------------------- | ------------------------------------------------ | -------------- |
| 橱窗查询与维护               | `getProductShowcase`，查询、维护和回读共用该绑定 | TOP            |
| SKU 库存                     | `getProductInventory`，`source: sku`             | TOP            |
| 商品级库存与评分             | 对应操作及参数                                   | 按共享注册表   |
| 订单聚合详情                 | `getTradeOrderAggregate`                         | TOP            |
| 图片、模板携图和 ZIP/S3 传输 | `listPhotos`，冻结完整流程绑定                   | TOP            |
| 独立图片上传                 | `uploadPhoto`；旧无参数语义不变                  | IOP            |
| 视频列表及关联核对           | 各自的实际只读操作                               | TOP            |
| 视频上传任务                 | `callCapability`，`alibaba.icbu.video.upload`    | TOP            |

只有 IOP 时，仍保留原有支持范围和图片分组校验。平台不支持或尚未验收的操作继续拒绝；不能过滤跨分组响应来伪造成功。

## 缓存、回执和恢复

- 页面身份与具体请求使用的配置分别校验；缓存包含实际请求配置，迟到结果不得写到新配置下。
- 新传输计划依赖完整流程选择配置。已有任务不自动改绑；不匹配时保留回执，要求检查或重新预览，不自动重复上传。
- 模板携图会检查同包同目标的旧回执，不能因协议上下文变更而将它当作全新上传。
- 任务中心按来源读取上下文，保留旧记录和配置变化状态。切换默认授权不是重放任务的指令。

## 验证方法

- 单测覆盖真实 BFF 客户端到 Hono 网关、扩展后台消息到最终请求，分别核对 TOP/IOP 两种默认偏好。
- 写入路由仅使用隔离样本验证；不因本次修复扩大写入白名单。
- `scripts/smoke-dual-context-read.ts` 使用两份本机授权包和临时内存数据库检查真实只读链路。需要显式的只读及同商家确认；不会修改当前配置、刷新 Token 或发送业务写入。
- 该脚本限制平台方法、总请求数和频率，只在忽略目录保存方法、协议、数量、requestId 和错误码，不保存完整业务响应或凭据。

真实检查的通过、合法空结果、权限不足和缺少前置数据分别记录；不能把契约测试或隔离回放当作平台写入验收。

## 本轮真实只读检查（2026-10-24）

- 远程 Node 使用隔离的双授权内存数据库，通过实际 BFF 上下文接口和业务接口检查选路：商品、图片分组和销售订单列表使用 IOP；橱窗、通用橱窗查询、SKU 库存、图片列表、视频和订单聚合使用 TOP。共发送 11 个平台只读请求，回执仅保存在忽略目录。
- 远程正式 MV3 构建沿用已有 TOP/IOP 配置及 IOP 默认偏好。重载后，橱窗管理正常读到两个位置；SKU 库存查询返回明确的空记录；订单聚合、图片和视频列表正常返回，不再被错误的 IOP 上下文阻止。
- 订单响应中的资金业务状态、未知物流及聚石塔限制保留原意；接口可读取不代表存在真实支付或完整订单详情。空库存不解释为零。
- 本轮没有修改橱窗、商品、库存、授权配置或默认协议，没有刷新 Token、重放任务或部署线上环境。历史写入保护通过隔离测试覆盖，不宣称已进行新的平台写入验收。

## 后续 API 登记

新增或重审方法同步更新离线协议清单，分开记录 TOP 方法名、IOP 路径、文档来源、适配状态及账号验证，不能根据描述文字或接口名称猜测协议。详见 [API 文档源策略](alibaba-api-document-sources.md#协议注册清单离线)。运行 `pnpm run check:protocol-registration` 检查清单漂移；该检查也进入 `generate:check`，不参与运行时选路或授予写权限。
