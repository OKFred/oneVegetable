# 凭证保险库

## 目标与边界

凭证保险库保留用户口令加密，但解锁后会在受信 `chrome.storage.local` 持久保存派生密钥材料，以便本机恢复会话。密钥材料和密文位于同一个浏览器配置文件，因此降低了对离线读取者的防护：复制完整浏览器配置文件的人可能无需口令就能解密。这是本机使用便利性，不是独立的密码保险箱，也不能保护被恶意软件控制的浏览器或替代高安全场景中的服务端 BFF。

## 密钥与密文格式

- 首次获取授权前可选设置 6–256 位本机保护口令；留空时使用随机本机密钥，不使用空口令派生密钥。口令本身从不写入 Chrome 存储、页面存储或日志；
- PBKDF2-HMAC-SHA256 使用每个保险库独立的 16-byte 随机 salt 和 600,000 次迭代；
- 派生 256-bit AES-GCM 密钥，运行时导入为不可导出的 `CryptoKey`，但原始派生密钥材料会单独持久保存；不能据此宣称持久密钥不可提取；
- 每次加密使用新的 12-byte 随机 IV、128-bit authentication tag 和固定 additional authenticated data；
- 密文记录保留原有版本、salt、IV 和 ciphertext 等格式，不包含凭证明文；另外的恢复记录包含派生密钥材料及其绑定的密文标识，不包含口令或明文 Token。

AES-GCM 同时验证密文完整性。错误口令、被修改的密文和不合法的设置都返回统一解锁错误，不把解析细节暴露给页面。

## 运行时生命周期

新版/旧版选择前先准备本机保护，已解锁时直接复用。授权工具与设置共用保护密钥，返回设置或导入刚取得的授权时无需再次设置口令；独立 TOP/IOP 凭据仍分别加密，不混用应用资料。已有且独立设置口令的旧工作台不被覆盖，手动锁定后仍需其原口令。

无口令模式的随机恢复密钥仅存受信本机存储；手动锁定后必须点击解锁才恢复，但不提供额外口令屏障。可以随后设置口令。此模式不是独立安全保险箱；复制完整浏览器配置可能读取凭据。初次准备、导入及口令轮换同时提交密文和恢复记录，写入失败不覆盖原状态。

工作台和独立 TOP/IOP 授权工具的恢复材料只写入 `TRUSTED_CONTEXTS` 的 `chrome.storage.local`，不进入 `chrome.storage.sync`、数据清单、诊断或状态响应。解锁后的明文凭据和运行时 `CryptoKey` 留在 service worker 内存；恢复时必须核对协议、salt、IV 和 ciphertext 并验证 AES-GCM 密文。持久材料丢失、失配或损坏时不继续使用旧内存授权，需原口令重新解锁或明确清除。

浏览器重启、扩展更新、重载或禁用后重新启用不再主动锁定；持久恢复记录完整时可恢复已有授权。工作台手动锁定同时锁定独立 TOP 和 IOP 授权工具；工具内单独锁定只影响所选协议。手动锁定清理内存及持久恢复密钥，之后重启仍保持锁定。工作台保留无密钥的 `{schemaVersion:2,state:'locked'}` 标记，阻止旧 `storage.session` 缓存再次迁移；独立工具没有旧会话缓存回退，删除各自恢复记录。锁定与清除使在途恢复失效，迟到的状态读取不能重新激活密钥。持久写入或删除失败会报告错误，不承诺已保存或已锁定，需用户重试。

不再空闲自动锁定，也不提供空闲超时选项；旧保险库中的空闲策略不再执行。OAuth 当前任务仍只驻内存并有 10 分钟有效期，后台重启后未完成的任务需重新发起，这不等于锁定已完成的授权包。未知换取／刷新回执仍阻止自动重试和导出；已轮换 Token 的本机保存失败可以重试保存，但不重发平台请求。

扩展启动时把 `chrome.storage.local` 和 `chrome.storage.session` 的访问级别设置为 `TRUSTED_CONTEXTS`，阻止网页及扩展内容脚本通过 Storage API 读取。由于该 API 自 Chrome 102 起提供，manifest 明确设置最低 Chrome 版本为 102。参考 [Chrome Storage API](https://developer.chrome.com/docs/extensions/reference/api/storage) 和 [扩展 service worker 生命周期](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)。

## 升级、轮换与恢复

旧版明文设置被识别为“待迁移”后不再参与真实请求。迁移由 service worker 读取旧记录、使用用户新口令加密并原位覆盖；options 页面不会收到旧 App Secret 或 Access Token。

更换工作台口令仍会生成新 salt 和新密钥并重新加密现有设置。旧版独立授权包没有持久恢复材料时继续保持锁定，必须使用原口令成功解锁一次，且恢复材料持久化成功后才启用重启恢复；不替换原口令、不丢弃旧密文。工作台可迁移有效的旧 `chrome.storage.session` 会话，但手动锁定标记优先。开发者不保存口令、托管恢复密钥或提供后门；手动锁定或恢复材料丢失后若忘记口令，只能明确清除并重新配置。清除授权或全部数据也会删除对应恢复密钥，既不撤销上游授权，也不删除用户另行导出的 JSON 文件。

## 验证范围

定向单元测试覆盖原口令密文兼容、派生材料恢复、TOP/IOP 隔离、旧包首次解锁、手动锁定与清除、持久化失败、未知刷新回执保留，以及迟到的状态恢复不能覆盖锁定。主流程另有 `tests/e2e/extension-persistent-unlock.spec.ts`，验证完整 Chrome 关闭／重启后的工作台和双协议恢复，以及工作台统一手动锁定后再次重启仍锁定。单元测试重建控制器不等同于真实浏览器生命周期验收；这些检查也不证明 Alibaba 上游接受了真实签名请求。
